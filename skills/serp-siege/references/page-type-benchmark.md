# Conditional Page Type Benchmark

Use this reference only after direct-competitor research, clustering, and the SEO Page Map are already stable. The purpose is to improve a small number of strategic page templates without turning SERP Siege into a broad UX-research project.

## Purpose

A cross-vertical page-type benchmark answers:

> How can this already-justified page be structured better?

It does **not** answer:

- whether the keyword has demand;
- whether a new page should exist;
- whether a cluster deserves P0/P1;
- whether the project should proceed;
- whether the site architecture should change.

Those decisions remain grounded in direct search, direct-competitor, supplied first-party, or upstream evidence.

## Trigger conditions

Run the benchmark only when at least one of these is true for a strategically important template:

- direct competitors are structurally weak, thin, outdated, or nearly identical;
- the template is P0/high leverage and its information architecture is unresolved;
- the primary CTA or task flow is unclear;
- preview/state handling is unclear;
- related-item discovery or internal linking is strategically important but weak in direct competitors;
- the page must balance SEO coverage with a meaningful product/conversion interaction and the direct-competitor pattern is insufficient.

## Skip conditions

Skip the benchmark when:

- direct competitors already provide a strong, reusable structure;
- there is no concrete page-structure question to answer;
- the candidate page is not in the current First Batch or another explicitly strategic template;
- the benchmark would delay the SEO MVP without resolving a material execution uncertainty;
- the only goal is to collect more inspiration.

## Hard research budget

For a normal SERP Siege run:

- benchmark at most **1–2 cross-vertical sites total**;
- apply the research to at most **1–3 strategic page templates**;
- perform **one benchmark pass**;
- extract at most **3 reusable patterns total**;
- stop immediately when the concrete page-structure question is answered.

Do not widen the benchmark because another interesting site appears.

## Choosing an analogous page

Prefer pages that share the same page archetype or interaction model, even when the product category differs. Useful analogies can include detail pages, tool workspaces, converters, viewers, download pages, directory items, asset pages, package pages, or other task-equivalent templates.

A source is transferable only when the selected pattern:

1. solves a comparable user task or information problem;
2. can work with the candidate's existing product core;
3. does not depend on a materially different business model, community, account system, or data moat;
4. does not require a new keyword cluster to justify it;
5. can be expressed as a concrete reusable page pattern rather than visual imitation.

## What to extract

Prefer structural patterns over decoration. Candidate pattern classes include:

- information hierarchy and module order;
- primary/secondary CTA mechanics;
- input, preview, result, empty, loading, and error states;
- metadata/trust blocks that reduce user uncertainty;
- related-item discovery and next-task pathways;
- internal-link modules tied to real adjacent intent;
- compact comparison, specification, or usage blocks where they improve task completion.

Do not copy brand styling, proprietary copy, irrelevant features, or an entire page wholesale.

## Transfer decision

For every extracted pattern, record one of:

- `ADOPT`: transferable with minimal change;
- `ADAPT`: useful principle, but must be reshaped for the candidate workflow;
- `REJECT`: interesting but creates unnecessary product, maintenance, or intent complexity.

Keep only `ADOPT` and `ADAPT` patterns in the execution plan, and never more than three total.

## Evidence discipline

- A live benchmark observation is `LIVE_PUBLIC_OBSERVATION` with a traceable source.
- A user-provided screenshot/export/example is `FIRST_PARTY` or `USER_SUPPLIED_THIRD_PARTY` according to provenance.
- A proposed transfer from the observed pattern is `MODEL_INFERENCE` unless separately supported.
- Never convert a page-pattern observation into keyword-volume, conversion-rate, traffic-ceiling, or ranking evidence.

## Allowed effect on the roadmap

The benchmark may refine:

- page module order;
- information architecture;
- CTA placement/behavior;
- preview and state handling;
- related-item discovery;
- internal-link structure;
- acceptance criteria for a page template.

It may **not**:

- create a new cluster;
- create a new page by itself;
- promote a cluster to P0/P1;
- expand the First Batch count;
- override a `HOLD` caused by missing demand evidence;
- change the user/upstream destination decision.
